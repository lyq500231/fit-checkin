## 2. 起因：一个不对的数字

第一版用 Termux 直接 `pkg install llama-cpp` 跑通了，`llama-bench` 报出的数据是这样的：

| 测试 | 线程 | 结果 |
|---|---|---|
| pp512（prefill） | t1 | 2.34 t/s |
| pp512 | t4 | 10.00 t/s |
| pp512 | t8 | 12.59 t/s |
| tg128（decode） | t4 | 6.72 t/s |

**单看 tg128 的 6.72 t/s，在 8 Gen 3 上不算离谱。** 真正可疑的是这个比值：

```text
pp/tg = 10.00 / 6.72 ≈ 1.6
```

为什么这是可疑信号：**prefill 是算力密集**（大矩阵乘，能吃到 SIMD / 点积指令），
**decode 是内存带宽密集**（每生成 1 个 token 要把全部权重读一遍，退化成单行 gemv）。
两者受制于**完全不同的上限**，所以任何一个偏离自己的上限就会被另一个暴露出来。

pp 只有 10 t/s 意味着：**prefill 根本没吃到 CPU 的向量能力**。问题不在模型、不在内存，而在**编译产物**。

> 复盘要点：端侧性能排查最有价值的信号往往不是"慢"，而是"**两个受制于不同上限的量，其中有一个明显贴着自己的上限**"。
> 单看一个 tokens/s 你什么也发现不了。

### 2.1 勘误（2026-11-06，F 完成后）：我原本写的 ">20 倍" 判据不适用于 CPU-only

本节旧版写过"正常 CPU 推理上 pp/tg 比值通常 **>20**"。**这个数值来自 GPU 场景的经验，在 CPU-only 端侧会误导**，
而且它正是你在面试里最容易被抓住的那种话。用 F 实测的两个绝对上限算就知道：

```text
tg 上限 = 实测流读带宽 49.9 / 2.4973 GB       ≈ 20.0 t/s     ← 实测 11.27~12.00，达成 56~60%
pp 上限 = 聚合 INT8 峰值算力 / (2 × 4.02 B)    ≈ 数十 t/s 量级 ← 实测 37.48，很可能已接近上限
⇒ pp/tg 在 8 Gen 3 上天然就是 2~4，而不是 20
```

**正确的判据是分别对照各自的天花板，而不是看一个跨设备的比值经验值。**
旧判据虽然把排查方向带对了（确实卡在编译指令集上），但那是**运气而非逻辑**——
一条数值错误的启发式也可能给出正确答案，这不能反过来证明它正确。

## 3. 取证：阳性对照反汇编法

不是猜"应该是编译参数问题"，而是把 `libggml-cpu.so` 反汇编出来，**数指令**。

```bash
# Termux 里 binutils 工具带 g 前缀
gobjdump -d $PREFIX/lib/libggml-cpu.so > /tmp/dis.txt
wc -l /tmp/dis.txt            # 175396 行

# ① 阳性对照：先证明"我的方法能数到东西"
grep -c 'ldr'    /tmp/dis.txt   # 16073
grep -c 'fmla'   /tmp/dis.txt   # 1542
grep -c 'scvtf'  /tmp/dis.txt   # 473

# ② 目标指令：INT8 点积 / 矩阵乘扩展
grep -cE 'udot|sdot|smmla|smmls|fmmla' /tmp/dis.txt    # 0
```

**为什么必须先做第①步**：如果直接跳到第②步看到 0，你无法区分两种可能——
(a) 真的没有这些内核；(b) 你的 grep 姿势错了 / 工具没装（本次 `iconv` 缺失就造成过一次 `&&` 走 `||` 分支的**假阳性**）。

> 任何"零结果"必须配一个阳性对照，否则它只是"我没测到"，不是"它不存在"。

**结论**：发行版 `armv8-a baseline` 编译，SIMD 只有最基础的 NEON（fmla 存在），**没有 dotprod / i8mm**，
所以 INT8 反量化+累加路径走的是标量/低效实现，prefill 被卡死。

## 4. 修复：按设备能力重编译

```bash
git clone https://gitcode.com/mirror/github/ggml/llama.cpp.git   # GitHub 直连不稳，用镜像
cd llama.cpp

cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DLLAMA_CURL=OFF \
  -DGGML_CPU_ARM_ARCH="armv8.2a+dotprod+i8mm+fp16"
cmake --build build --config Release -j
```

- `GGML_CPU_ARM_ARCH` 是 llama.cpp 提供的显式覆盖口，让 arm64 编译带上 `+dotprod+i8mm`。
- `LLAMA_CURL=OFF`：Termux 里 libcurl 依赖容易把构建带崩，我们不需要从 URL 拉模型。

**实际生效的编译 flags（从 build 日志确认，而不是"我以为生效了"）：**

```text
-mcpu=native+dotprod+i8mm+nosve+nosme     OpenMP 5.1 已启用
```

产物落在 `~/llama.cpp/build/bin/`，含 `llama-bench`、`llama-perplexity`、`llama-quantize`、
`llama-imatrix`、`llama-vdot`、`llama-q8dot`、`llama-server`。

## 5. 收益：同一台机器、同一模型，只换二进制

| 测试 | 发行版 0.8.0（baseline） | 自编译（dotprod+i8mm） | 倍数 |
|---|---|---|---|
| pp512 t1 | 2.34 | **10.60** | ×4.53 |
| pp512 t4 | 10.00 | **37.48** | ×3.75 |
| pp512 t8 | 12.59 | 30.61 | ×2.43 |
| tg128 t4 | 6.72 | **11.35** | ×1.69 |
| tg128 t8 | 6.11 | 8.28 | t8 负收益 |

**读这张表的方式（面试会被问）：**

1. **prefill 提升 3.7~4.5 倍** → 它是算力/指令密集，缺点积指令直接卡在这里，符合预期。
2. **decode 只提升 1.69 倍** → 它受**内存带宽**限制，指令优化收益有限。这条差距本身就是"decode 是带宽瓶颈"的旁证。
3. **t8 全面负收益**（pp 30.61 < t4 37.48；tg 8.28 < 11.35）→ 8 Gen 3 是 1+5+2 大小核，
   线程开到 8 会落到小核并引入同步开销。**所以服务固定 `-t 4`。**
4. 结论不是"我调参变快了"，而是"之前那份二进制没有针对这台设备的指令集编译"。

### 5.1 复测（2026-11-06：冷机、拔充电器、`-p 0 -n 128 -t 1,4,8 -r 5`）

| 测试 | 首轮 | 复测 | 采用值 | 取舍理由 |
|---|---|---|---|---|
| tg128 **t1** | 3.46 ± 1.88 | **4.30 ± 0.01** | **4.30** | 首轮变异 54% 弃用；复测方差 0.2%，且 4.30×2.4973=10.74 GB/s 落在单核可行区间 |
| tg128 **t4** | 12.00 ± 0.58 | — | **12.00** | 比上表 11.35 快 5.7%，同向（机器更冷、后台更少），属正常抖动 |
| tg128 **t8** | 9.04 ± 0.34 | — | **9.04** | 与 8.28 同向，**`t8 < t4` 两次独立复现** |

⚠️ **一个我自己犯的指标混淆**（写下来防自己再犯、也防你照抄错）：
§5 表里的 `10.60` 是 **pp512 t1（prefill）**，不是 decode。我一度把它当成"decode t1 的历史值"去和新的 4.30 对比，
于是断言"两轮数据互相打脸"。拿物理一算就明白 4.30 才对：`4.30 × 2.4973 GB = 10.74 GB/s`（单核合理），
而 `10.60 × 2.4973 = 26.5 GB/s`——**单核不可能**。
**同一个 `t1` 后缀，前缀 pp 与 tg 之间是两个世界。** 读别人的 benchmark 先确认这一点。

## 6. 端侧教练闭环是怎么搭起来的

```text
┌──────────────────── iQOO 12（全部本地，无外网）────────────────────┐
│                                                                    │
│  llama-server  -m ~/models/Qwen3-4B-Q4_K_M.gguf                    │
│                --host 127.0.0.1 --port 8080                        │
│                -c 4096 -t 4 -np 1                                  │
│                --path ~/ai-coach   ← 同时托管前端静态文件            │
│                                                                    │
│   http://127.0.0.1:8080/coach.html      （页面）                    │
│   http://127.0.0.1:8080/v1/chat/completions （OpenAI 兼容接口）      │
└────────────────────────────────────────────────────────────────────┘
```

- **同源托管**是关键设计：页面和推理接口在同一个 `127.0.0.1:8080`，
  于是**不需要 CORS、不需要 HTTPS 混合内容豁免、不需要任何服务器**，一个进程全解决。
- 注意参数名：`--path`（`--public-dir` 不存在）。
  **教训：不要凭记忆写参数，一律先 `--help` 确认。**
- 数据输入：`~/ai-coach/week.json`（每周训练摘要），页面组装成 prompt 交给模型。
- 后台运行：`nohup ... > ~/server.log 2>&1 &`。

**最终形态实测**：一次完整教练请求 **7.25s**（输出 60 tok @ 10.70 tok/s），回答是结构化的中文教练分析。

## 7. 有效带宽：分母实测完成，"34%→58%" 两个数字都被证实（**已定稿**）

> 复核日期 2026-11-06。方法：**同一二进制、同一 1024MB int64 常驻数组，只改线程数**，
> 用 OpenMP 多线程流读实测带宽上限；分子取 `llama-bench -p 0 -n 128`。全程冷机、拔充电器、逐档 sleep。

### 7.1 公式与它的前提

decode 每生成 1 个 token 要把全部权重读一遍，所以：

```text
BW_eff = tokens/s × 每 token 读取字节数 ≈ tokens/s × 模型文件字节数
每 token 字节数 = 2497280256 B   ← 用 sha256 校验过的实际文件大小，不是"4.5bit × 参数量"的推算值
```

**这个前提已经实测（待办 J，2026-11-06），结果见 §7.3.1。** 顺带记录一个**实验设计错误**：
我最初把 J 写成"`-c 2048` vs `-c 8192`"，但 **`-c` 只是 KV 缓冲区的容量，不产生任何真实 token**，
用它做敏感性对比两档必然完全相同 → 你会拿到一个"前提成立"的**空结果**，却以为自己验证过了。
**空结果比错误结果更危险：错误会触发怀疑，空结果不会。** 正确的自变量是 `-p`（实际 prefill 长度）。
### 7.2 分母：这台机器实际能给多少带宽（两轮独立复测）

| 线程 | 第一轮 MAX | 第二轮 MAX（冷机、先跑） | 采用值 | 复现性 |
|---|---|---|---|---|
| T=1 | 30.99 | 与**独立实现** `bw1` 的 34.25 交叉印证（差 9.5%） | **30.99** | 6 遍 ±2% |
| **T=4** | 50.47 | 49.36 | **49.9** | **两轮只差 2.2%** |
| T=8 | 26.86 | 22.10 | **24.5** | 复现，但方差大（见 7.5） |

理论峰值 LPDDR5X-8533 × 4×32bit = **68.3 GB/s**；本机纯流读实测最高只有 **49.9 GB/s（理论的 73%）**。
**这就是"占理论峰值百分之几"这个口径的原罪：它天生吃亏，而且不可复现。**

### 7.3 对账：那两个数字都是对的

| 轮次 | t/s 实测 | BW_eff | ÷ 实测上限 49.9 | ÷ 理论 68.3 |
|---|---|---|---|---|
| 发行版 0.8.0（无 dotprod/i8mm） | 6.72 | 16.78 GB/s | **33.6%** ← 就是那个 "34%" | 24.6% |
| 自编译（dotprod+i8mm） | 11.35 | 28.34 GB/s | **56.8%** ← 就是那个 "58%" | 41.5% |
| 同二进制复测 | 12.00 | 29.97 GB/s | **60.1%** | 43.9% |

> **原来的 "34% → 58%" 被完整证实，误差 1 个百分点以内**——前提是分母取**实测 4 线程流读上限 49.9 GB/s**。
> 我在本节旧版里写过"58% 推不出来、可能是 42%"：那是因为我手里**只有理论峰值、没有实测分母**。
> 于是这一节把它自己的方法论给证实了：**没有分母的百分比不是数据，是修辞。**

### 7.3.1 KV 到底值多少钱：一个常数系数被三点数据推翻

**先记录方法学**：`0.65` 这个系数是从 `p=4096` **单点反推**的，所以它必然完美解释 p=4096。
我差点把"预测 9.77 / 实测 9.74"当成验证——**那是自我符合，不是检验**。真正的检验只能用其他三点（`-p 512/2048/8192`）。

实测（同机、同二进制、`-n 128 -t 4 -r 3`）：

| p | tg128 实测 t/s | 名义 KV (GB) | 若系数=1 的预测 | 若系数=0.65 的预测 | 0.65 模型偏差 |
|---|---|---|---|---|---|
| 512 | 10.55 ± 0.59 | 0.074 | 10.80 | 11.06 | **−4.6%** |
| 2048 | 9.88 ± 0.42 | 0.294 | 9.35 | 10.47 | **−5.6%** |
| 4096 | 9.74 ± 0.52 | 0.588 | 8.13 | *(拟合点，无预测力)* | — |
| 8192 | 9.40 ± 1.48 | 1.176 | **7.66** | 8.63 | **+8.9%** |

用每档反解"有效每 token 流量 = BW_eff(p0) ÷ t/s"，规律立刻浮现：

| p | 反解流量 (GB/token) | 其中超出权重的部分 | 超出部分 ÷ 名义 KV |
|---|---|---|---|
| 512 | 2.667 | 0.170 | **2.32** |
| 2048 | 2.848 | 0.351 | **1.20** |
| 4096 | 2.889 | 0.392 | **0.67** |
| 8192 | 2.994 | 0.497 | **0.42** |

**系数从 2.32 一路降到 0.42 —— 它根本不是常数。** 这个形状说明两件事：

1. **存在一个与 p 无关的固定开销**：约 **0.15 GB/token**（权重 2.497 + 0.15 = 2.65 的截距），来自激活、attention kernel 启动、每 token 的调度；短上下文时它被摊到很小的 KV 上，于是"系数"看起来巨大（2.32）；
2. **KV 的长期边际价格只有名义值的 ~29%**：对 512→8192 做线性拟合，斜率 = `0.0426 MB/token`，而名义 KV 是 `0.147 MB/token` ⇒ **0.29**。

于是得到一个**拟合两点、第三点独立验证**的更好模型：

```text
每 token 有效流量 ≈ 2.645 GB + 0.0426 MB × p          （斜率/截距由 p=512 与 p=8192 两点确定）
  ⇒ 预测 p=2048 = 28.14 / 2.732 = 10.30 t/s，实测 9.88 → 偏差 −4.1%（未参与拟合的点）
  ⇒ 预测 p=8192 =  9.40 t/s（拟合点）
```

**结论（可发表版）**：

> decode 的每 token 流量约 `2.65 GB + 0.043 MB×上下文长度`。其中权重 2.497 GB 是不可压缩主体；
> **KV 的有效带宽价格约为其名义字节的 29%**——因为 KV 是大块规则流式访问，预取友好且能与 gemv 计算重叠，
> 而权重访问是跨层大跨度读。这解释了为什么上下文从 512 涨到 8192、名义字节数 **+47%**，
> 吞吐却只掉 **16.6%**（若严格带宽受限，应掉 32%）。

**对 §7.3 的影响 —— 以及我第二次差点踩进同一个坑。**
这一节初稿在这里写的是：「把 4K 上下文的价格算全，`9.74 × 2.889 = 28.14 GB/s`，与 p=0 时相同，
所以带宽受限得证。」**那个 2.889 GB 正是用 `28.14 ÷ 9.74` 反推来的**，两数相等是定义使然。
同一个错误我在这一小节里犯了两次，第二次是在我已经写下警告之后。已删除。

能说的只有**模型之间的比较**（下面的预测值全部由「名义字节 × 折扣」独立算出，不来自实测反推）：

| 模型 | 参数个数 | p512 | p2048 | p4096 | p8192 | 最大偏差 |
|---|---|---|---|---|---|---|
| 名义字节，系数=1 | **0** | −2.3% | +5.7% | **+19.8%** | **+22.7%** | 22.7% |
| KV 折扣 0.65 | 1 | −4.6% | −5.6% | 拟合点 | +8.9% | 8.9% |
| KV 折扣 0.29 + 固定开销 0.15 GB | 2 | 拟合点 | **−4.1%**（独立点） | 拟合点 | 拟合点 | 4.1% |

于是诚实的表述只剩三条：

1. **带宽是主导约束**——成立。证据是 t/s 随每 token 流量单调下降，且**零参数**的名义模型在 p≤2048 就能把误差压进 6%；
2. **「恒定 BW_eff」没有被证明**——它是用来拟合折扣系数的**假设**，不能反过来当结论引用；
3. **56%~60% 这些数字依然可用**，因为分子用的是独立可查的权重名义字节（sha256 校验过的 2.497 GB），分母是独立实测的 49.9 GB/s，两者之间没有循环。
   但必须标注口径：**只计权重流量**。

> 本节最终留下的最有价值的东西不是那个系数，而是**一个被记录下来的错误**：
> 用测量结果反推模型参数，再用同一批数据宣布模型成立。
### 7.4 附带结论：选线程数要看**绝对带宽**，看利用率会做错决策

| 线程 | llama t/s | BW_eff | ÷ 同档上限 | 判读 |
|---|---|---|---|---|
| t1 | 4.30 ± 0.01 | 10.74 | **34.7%** (÷30.99) | 单线程连自己的带宽都没用满（能发出的访存请求有限） |
| **t4** | **12.00 ± 0.58** | **29.97** | 60.1% (÷49.9) | **甜点：绝对带宽最高，利用率还留有余量** |
| t8 | 9.04 ± 0.34 | 22.58 | **92.2%** (÷24.5) | 几乎榨干当时拿到的带宽，可**带宽本身塌了一半** |

**"8 线程为什么反而慢"第一次有了机理答案**：不是同步开销，而是**可用带宽从 49.9 塌到 24.5**。
讽刺的是 t8 的利用率最高（92%）——**利用率最高的那一档，吞吐最低**。
这条比 58% 更能体现端侧判断力：**优化目标是绝对吞吐，不是把某个百分比填满。**

### 7.5 T=8 两轮内部趋势相反 → 是调度非确定性，不是热降频

- 第一轮 rep 序列**下滑**：26.86 → 26.57 → 23.63 → 23.84 → 25.79 → 12.73
- 第二轮（冷机先跑）**上升**：17.43 → 16.79 → 15.18 → 19.09 → 20.33 → 22.10
- 趋势相反 ⇒ 排除单调热漂移；符合 1+5+2 大小核下**内核把线程迁移到不同核组合**造成的方差
- 待办 I：`taskset` 分别绑满大核 / 绑小核各测一轮，把"调度"与"带宽"彻底分离（不影响 7.4 的结论，因为两轮都远低于 T=4）

### 7.6 统计量本身也是口径（同一批数据可以讲成两种故事）

`MAX T=4 = 50.47` 来自第一轮最好的一遍，而那一轮里 `rep=4 = 31.57` 明显离群。定稿取**两轮 MAX 的平均 49.9**：

- 取 MAX：分母最大 → 利用率最小 → **对自己最不利的算法**（我故意选它）
- 取去离群均值：分母 48.8 → 利用率 61.4% → 数字更漂亮，但不可复现

**报告自己的性能时，主动选那个让结论变弱的算法。** 这是本节最想留下的一条。

### 7.7 本轮测法踩的五个坑（详见 §10）

| 坑 | 错误结果 | 正确做法 |
|---|---|---|
| 多进程各自 MAX 相加 | **97.99 GB/s**（超理论峰值，一眼假） | 同地址空间多线程；或总流量 ÷ 同一时间窗 |
| first-touch/缺页算进墙钟 | **5.81 GB/s**（测成了页表建立速度） | 预热写在计时循环之外；必要时丢弃首轮 |
| Python `Pool` 顶层无 `__main__` 保护 | Android forkserver **无限递归**崩溃 | 端侧并行用线程，不用进程 |
| `aligned_alloc` | 编译失败（bionic 要 API≥28 + C11） | 用 `posix_memalign`（API 21+ 恒定可用） |
| 并发场景仍用 MAX | 双计峰值 | 用均值/中位数，并写明为何选它 |

## 8. 三个非性能但同样值钱的效果项

### 8.1 `enable_thinking: false`（Qwen3 的 thinking 模式）

| 配置 | 结果 |
|---|---|
| 不关 thinking | `content` 为**空**、`finish_reason: length`、80 tok 全被思考过程吃掉、6.49s |
| `chat_template_kwargs: {"enable_thinking": false}` | 58 tok、`finish_reason: stop`、**4.40s** |

省 2.1s，同时**修好了"回答是空的"这个 bug**。在端侧小模型上，思考模式会把有限的 token 预算全部消耗在不可见内容上——
**这是一个纯粹由端侧约束（token 预算小 + 延迟敏感）暴露出来的问题**，云端大模型上你根本不会注意它。

### 8.2 KV Cache 前缀复用（以及它带来的测量陷阱）

`f_sim_best = 1.000`，260 token 的重复前缀只重算了 **1 token**，首字节延迟 **0.01s**。

⚠️ 但这条数据**不能当作真实首字延迟**：因为反复用同一个 prompt 时前缀缓存命中。
**做 A/B 实验必须更换 prompt**，否则你在测缓存而不是测模型。这是我这次踩到的最隐蔽的坑。

### 8.3 并发

4 个 slot 并发（`-np 4`）把单请求 4.8s 拖到 **19~30s** → 定 **`-np 1`**。
移动端 CPU 核心与带宽本就有限，并发只会让每个请求都变慢，单用户场景串行是正确取舍。

---

### 8.4 prefill 的真实代价曲线（以及它为什么和端到端 7.25s 不打架）

`-p` 扫描顺带测出 **pp 吞吐随长度显著下降**（llama-bench 每档都是冷启动全量 prefill）：

| prefill 长度 | pp t/s | 单独 prefill 耗时 |
|---|---|---|
| 512 | 36.87 ± 1.23 | 13.9 s |
| 2048 | 29.37 ± 0.07 | 69.7 s |
| 4096 | 21.90 ± 3.39 | 187 s |
| 8192 | **15.43 ± 0.72** | **531 s** |

矛盾来了：`coach.html` 注入约 210 token 摘要，按 36.87 t/s 应该要 **5.7 秒**首字；
可 §6 的端到端只有 **7.25 秒**，其中 decode（60 tok @ 10.7 t/s）已占 5.6 秒 → 留给 prefill 只剩 **1.6 秒**。

答案就是 §8.2 的 **KV 前缀复用**：system 提示词 + 摘要这两段在重复请求里是固定前缀，命中缓存后几乎不重算。
两边数据因此自洽，并导出一条产品级结论：

> **端侧对话的延迟优势主要来自前缀缓存，而不是模型跑得快。**
> 反过来，一旦摘要变了（每天新的训练记录），前缀失效 → 那 210 token 得真算，首字立刻回到秒级。
> `coach.html` 的 `renderBudget()` 之所以把"冷启动 / 稳态"两档都显示出来，就是为了把这件事摊开，而不是藏起来。

⚠️ **适用域声明**：页面里写死的 `PP_TPS = 37.5` 只在 **prefill ≤ 512 token** 时成立，长上下文会明显偏离（8192 只剩 15.4）。
教练场景约 210 token，在有效域内；但**任何把摘要加长的改动，都必须重新核对这一条**（这正是 §13.4 预算反解为什么要按 ctx 而不是按字符数）。

## 10. Termux / Android 踩坑清单（按血泪程度排序）

1. ⚠️ **`>` 会在执行命令前就截断目标文件**。写成果文件一律 `xxx.new` → 校验内容 → `mv` 覆盖。
2. ⚠️ 上千字节、含 `'` `$` 或中文的代码**不要用 heredoc 手粘**；用 **gzip+base64**（纯 `A-Za-z0-9+/=`）传，
   或把数据改成纯 ASCII；heredoc 定界符**必须带引号** `<<'EOF'`。
3. ⚠️ 管道右端接 `tail/sort/uniq/wc/head` 曾造成"假死"/吞输出；`curl` 调试**禁用 `-s`**，用 `-v` / `-i` / `-w`。
4. ⚠️ 报 `command not found` 先怀疑改名：Termux binutils 是 `greadelf` / `gobjdump` / `gstrings`。
5. ⚠️ 零结果必须配阳性对照（`iconv` 缺失曾导致一次假阳性）。
6. 网络：Termux 必须换国内源 + `Force-IPv4`；GitHub API 不稳，参数名一律从 `--help` 取。
7. USB adb 不可用：iQOO 的 ADB 接口未注册 `DeviceInterfaceGUID`（Service=WINUSB，但 `MI_02` 无 Device Parameters）。
   可行通道：手机浏览器下载 / 微信文件传输 / 未来试 `adb pair` 无线调试。
8. 流式 UI：vivo 浏览器对本地 XHR 的流式返回不友好，需换 Via / Edge 验收（非代码问题）。
9. ⚠️ **`pkg install openmp` 会报 Unable to locate package**——Termux 的 `omp.h` / `libomp` 由 **clang 包自带**，`clang -O2 -std=gnu11 -fopenmp` 直接可用。别为了一个不存在的包怀疑整条工具链。
10. ⚠️ **`aligned_alloc` 在 Termux 编译失败**：bionic 里它要 `__ANDROID_API__ ≥ 28` **且** C11 才在 `<stdlib.h>` 声明；而 `clang -dM -E -` 里 `__ANDROID_API__` 只是 `__ANDROID_MIN_SDK_VERSION__` 的别名，还得再展开一层才看得到数值。**跨端 C 一律优先 `posix_memalign`（API 21+ 恒定可用）**，并用 `-std=gnu11`（GNU 方言，避免严格模式下特性宏藏函数）。
11. ⚠️ **Termux 的 `/tmp` 不可写**：`> /tmp/x.txt` 直接 `Permission denied`，而子 shell 的 `Exit 1` 会让人误判成"进程被 OOM 杀了"。改用 `~/f/` 或 `$TMPDIR`。
12. ⚠️ **Termux 没有 `dumpsys`**（Android 系统服务不暴露给 Termux）。测温/查频改用 sysfs：
    `cat /sys/class/thermal/thermal_zone*/temp`、`cat /sys/devices/system/cpu/cpu*/cpufreq/scaling_cur_freq`。
13. ⚠️ **Android 上别用 Python 多进程测性能**：Python 3.14 默认 `forkserver`，子进程会**重新 import 主模块**——顶层 `Pool(T)` 直接无限递归崩掉。而且没有 COW 共享，数组也不白送。**端侧并行请用线程（OpenMP/pthread），不要用进程。**
14. ⚠️ **并发带宽不能把各 worker 的 MAX 相加**：worker 起跑不同步，各自的峰值出现在不同时刻，相加得到 97.99 GB/s——**超过理论峰值 68.3**，一眼假却很容易自我说服。同地址空间多线程，或"总流量 ÷ 同一时间窗"。
15. ⚠️ **first-touch 缺页会把带宽测成页表建立速度**：首轮 0.53 GB/s vs 稳态 29 GB/s（相差 50~60 倍）。预热必须在计时循环之外，必要时丢弃首轮；本次"总流量÷总墙钟"给出 5.81 GB/s 就是这么废掉的。
16. ⚠️ **`> file` 遇上进程 abort 会整批丢输出**：stdout 重定向是块缓冲，OpenMP 析构 SIGABRT 在 flush 之前发生 → 文件是空的。测可能崩的基准时**先看屏幕**，确认稳定再重定向。
17. ⚠️ **`pp512 t1` ≠ `tg128 t1`**：同一个 `t1` 前缀不同是两个世界（本仓库 §5.1 里我因此误判过一次）。

## 13. 教练数据契约，以及一个用实测才暴露出来的缺陷

### 13.1 数据是怎么接上的

主项目 `app.js` 新增**只读导出层**（对既有代码 **0 行修改**，git diff 为 `+59 insertions, 0 deletions`）：

```js
coachWeekJSON(weekOffset)  // 生成教练用的周摘要（0=本周，-1=上周；本周为空自动回退上周）
exportCoachJSON()          // 下载 week.json，供 ~/ai-coach/week.json 使用
```

契约（与旧 `week.json` 样例**向后兼容**，`coach.html` 一行都不用改）：

| 字段 | 类型 | 状态 | 说明 |
|---|---|---|---|
| `week` | `"2026-W45"` | 兼容 | ISO 周号（自实现 `isoWeekLabel`） |
| `days[].date` | `"11-02 周一"` | 兼容 | 与样例同格式 |
| `days[].items[].name` | string | 兼容 | **负重写进 name**：`杠铃卧推（40kg）` |
| `days[].items[].pass` | boolean | 兼容 | 取 `entryStat(e).done`，与产品判定同源 |
| `days[].items[].sets[].done/target` | number | 兼容 | 每组实际次数 / 达标线次数 |
| `days[].planName`、`days[].rest`、`items[].reps`、`items[].targetSets`、`sets[].weight`、`settings` | — | **新增** | 供 `coach.html` 以后取用；当前被安全忽略 |

**为什么负重塞在 `name` 里而不是独立字段**：`coach.html` 组装 prompt 的代码是
`it.name + ' ' + sets.map(s=>s.done+'/'+s.target).join(' ')`——只有 name 会进模型上下文。
**端侧的第一约束是 token 预算，任何"信息量"必须挤进已经会发送的字段里**，这是云端 API 项目开发时不会遇到的思维方式。

### 13.2 一个语义 bug（动态验证才发现，静态看代码看不出来）

初版把每组 `target` 取成了次数区间的**上限**（`parseReps("6-10").max`），于是导出数据长这样：

```text
杠铃卧推  7/10  8/10  8/10  6/10   pass: true     ← 自相矛盾
```

FitCheck 的达标判定用的是**下限**（`setOk: reps >= r.min`），所以四组"没到 10"依然全部达标。
数据送到模型面前，它会认为"每组都没完成目标却标记达标"，进而给出**错误的加重量建议**。

修复：`target = r.min || r.max`，让 `done/target` 与 `pass` 同源。
复验断言：`inconsistent = 0`（pass=true 时不存在"所有组都低于 target"的动作）。

> 复盘要点：**契约兼容 ≠ 语义正确**。字段名对、类型对，但含义错——这种 bug 只有把真实数据跑出来、
> 并按消费方（prompt 文本）的视角检查才会暴露。所以我这次的做法是：
> 在测试页里**复刻 coach.html 的 prompt 渲染函数**，直接看模型将读到什么字符串。

### 13.3 640 字符预算：实测确实会截断 → 已由分级压缩引擎解决（C1 定稿，见 §13.4）

用示例数据实测 `coach.html` 的 `summarize()` 输出长度：

| 数据范围 | 天数 | prompt 字符数 | 结果 |
|---|---|---|---|
| 本周（`offset=0`） | 2 | 292 | ✅ 安全 |
| 上周（`offset=-1`） | 5 | **674** | ⚠️ **超过 640，尾部被截断** |
| 两周前 | 5 | 634 | ⚠️ 压线 |
| 全量 JSON 备份直接喂 | — | 84514 | ❌ 完全不可行 |

这不是"把 640 改大"就能解决的事——674 个中文字符约等于 **600+ token**，
在 prefill 37.48 t/s 下是 **~16 秒** 的首字延迟（已经超过 `renderBudget()` 里自己设的 12 秒体验阈值）。
**640 是护栏，不是偷懒。**

正确解法不是"把 640 改大"，而是**把摘要做成会自己缩水的层级**。已实现，见 §13.4。

### 13.4 压缩引擎：6 级降级 + 由输出上限反解预算

**（1）预算不拍脑袋，由延迟反解。** 端侧真正稀缺的是秒，不是字符：

```text
decode = maxTok / TG_TPS                                   // 输出上限先吃掉多少秒
cold   = (SEC_COLD - decode) × PP_TPS - sysTok - qTok      // 冷启动（服务端无 KV 前缀）
warm   = (SEC_WARM - decode) × PP_TPS - qTok               // 稳态（system 已命中 KV，几乎不重算）
ctx    = min(cold, warm)                                   // 摘要只允许花这些 token
```

实测反解（sysTok=84、qTok=10，常量全部来自 iQOO 12）：

| 输出上限 | decode 占时 | 摘要预算 | 判定 |
|---|---|---|---|
| ≤60 tok | 4.4 s | **113 tok** | 可行 |
| ≤120 tok | 8.9 s | 稳态为负 → 触底 64 tok | **hopeless** |
| ≤200 tok | 14.8 s | 同上 | **hopeless** |

> **本次最重要的一条结论：默认值"输出≤120"自己就把稳态延迟预算吃满了，摘要怎么压都救不回来。**
> 所以页面在 hopeless 时不再假装成功，而是明写"光是生成到输出上限就要 8.9s，请把输出降到 ≤60"。
> 第一版实现犯过两个典型错误，都是测试逼出来的：① 地板值 `max(48,…)` 制造了"还有预算"的假象；
> ② hopeless 时干脆不压缩，把 458 tok 全塞进去 → 冷启动 **23.6s**。**"假装治好"和"放弃治疗"都是错的。**

**（2）牺牲顺序固定：先丢达标项的细节，最后才丢未达标项。** 教练需要的是异常，不是流水账。

| 级别 | 做法 | 样例 |
|---|---|---|
| L0 | 原始，不压缩 | `11-02 周一：杠铃卧推（40kg） 8/6 8/6 8/6 7/6` |
| L1 | 相邻同组合并 + 短名 + 短日期 + ✗ | `11-02 杠铃卧推40kg 8/6×3 7/6` |
| L2 | 达标项只留组数 | `杠铃卧推4组✓` |
| L3 | 达标项极简、`·` 连接 | `杠铃卧推4·侧平举3` |
| L4 | 达标项按天聚合（用 planName） | `推日 · 胸肩三头3项9组✓` |
| L5 | 只留最近 3 天，含未达标的天优先 | — |
| L6 | 仍超预算 → 硬截断并写明 | `…｜L6 超预算已截断` |

压缩效果（`app.js` 真实导出的三份周数据）：

| 样本 | 天数/动作 | L0 字符(tok) | L1 | L4 | 输出≤60 落点 |
|---|---|---|---|---|---|
| 正常周 | 6d/27 | 732 (458) | 653 (409) | 138 (87) | **L4 · 94 tok ✅** |
| 多项未达标 | 5d/23 | 616 (385) | 536 (335) | 246 (154) | **L5 · 109 tok ✅** |
| 大量未达标 | 5d/22 | 629 (394) | 545 (341) | 356 (223) | **L6 · 117 tok ✅** |

L0→L4 最大压缩 **81%**（732→138 字符）；3 份样本 × 3 档输出上限共 12 个组合，**全部落在预算内**。

**（3）信息取舍是产品决策，不是技术残渣。** 最狠那份样本 L6 只保住 6/10 个未达标动作——我没有靠"再挤一挤"糊过去，
而是让文本显式携带 `｜L6 超预算已截断`，配合 `SYSTEM_PROMPT` 第 2 条"记录不足时明确说信息不够并指出缺哪一项"，
模型会主动承认自己看不全。**在端侧，让模型知道自己看不全，比假装看得全更有用。**

### 13.5 测试资产：测的就是会上线的那段代码

`_test/coach-compact.test.js` → **`FAILS=0/45`**。两个刻意的设计：
